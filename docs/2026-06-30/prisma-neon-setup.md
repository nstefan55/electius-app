# Prisma + Neon PostgreSQL Setup

Database layer for Electious: **Prisma 7** ORM against **Neon** serverless PostgreSQL.
This doc is for developers and collaborators working on the project.

## TL;DR

```bash
# 1. Get the dev-branch connection strings from the Neon console and put them in .env
cp .env.example .env        # then fill DATABASE_URL (pooled) + DIRECT_URL (direct)

# 2. Apply migrations to your local dev branch
npx prisma migrate dev

# 3. (optional) Seed the dashboard demo data
npx prisma db seed

# 4. Sanity-check the connection
npx tsx scripts/test-db.ts
```

## Stack

| Piece | Package | Notes |
| ----- | ------- | ----- |
| ORM | `prisma` + `@prisma/client` 7.8.0 | Prisma 7 (breaking changes vs v6 — see below) |
| Driver adapter | `@prisma/adapter-neon` | Required in v7; pooled runtime queries |
| Neon driver | `@neondatabase/serverless` | Serverless-friendly Postgres driver |
| Server guard | `server-only` | Build-time error if the client leaks into a browser bundle |
| Seed runner | `tsx` (dev) | Runs the TypeScript seed/scripts |

## Environment variables

Two connection strings, both pointing at the **same Neon branch** (use `development`
locally, never `production`):

| Var | Connection | Host | Used by |
| --- | ---------- | ---- | ------- |
| `DATABASE_URL` | **Pooled** (PgBouncer) | has `-pooler` | App runtime, via the Neon adapter |
| `DIRECT_URL` | **Direct** | no `-pooler` | Prisma CLI: migrations, introspection |

Why two: a transaction pooler can't run DDL or advisory locks, so migrations need the
direct connection; the pooled one is better for per-request serverless runtime.

`.env` is gitignored. `.env.example` is the committed template — copy it and fill in.
Both strings come from the Neon console → project **electious** → branch → **Connect**.

## Key files

| File | Role |
| ---- | ---- |
| `prisma/schema.prisma` | Models + enums. `datasource` block holds only `provider` (URLs live in config) |
| `prisma.config.ts` | Prisma 7 config: schema/migrations paths, `datasource.url = DIRECT_URL`, seed command |
| `src/lib/prisma.ts` | `server-only` PrismaClient singleton over the Neon adapter (pooled `DATABASE_URL`) |
| `prisma/seed.ts` | Idempotent seed from `src/lib/mock-data.ts` |
| `scripts/test-db.ts` | Standalone connectivity + row-count check |
| `src/generated/prisma/` | Generated client — **gitignored**, regenerated by `prisma generate` |

## Using the client

```ts
import { prisma } from "@/lib/prisma";

const elections = await prisma.election.findMany({
  where: { status: "ACTIVE" },
  include: { _count: { select: { voters: true, votes: true } } },
});
```

The client is generated to `src/generated/prisma` (not `node_modules`). Because that
folder is gitignored, `prisma generate` runs automatically on `postinstall` and at the
start of `build` (`prisma generate && next build`).

## Prisma 7 gotchas (vs v6)

- **`prisma-client` generator** (not `prisma-client-js`) with a mandatory `output`.
- **Driver adapter required** — no implicit connection. We pass `PrismaNeon` to `new PrismaClient({ adapter })`.
- **URLs moved to `prisma.config.ts`** — the schema `datasource` block has no `url`/`directUrl`.
- **`migrate` no longer auto-runs `generate`** or seeds — both are explicit (`prisma generate`, `prisma db seed`).

## Migrations workflow

Always migrate; **never** `prisma db push`. Migrations are versioned files committed to
the repo so dev and prod stay in sync.

```bash
# Local development (creates + applies a migration on the dev branch)
npx prisma migrate dev --name <change>

# Production (apply existing migrations only — run before the app starts)
npx prisma migrate deploy

# Check sync state
npx prisma migrate status
```

Neon has two branches under the `electious` project: `development` (day-to-day work)
and `production`. Local `.env` points at `development`; promoting schema to production
is a separate `prisma migrate deploy` against the production connection string.

## Schema highlights

- **Voter anonymity is structural:** `Vote` has no `voterId` and no relation to `Voter`.
  Linking them would require an auditable migration — it's not just app-layer discipline.
- **Token security:** `VoterToken.hash` stores only `SHA-256(rawToken)`; the raw token is never persisted.
- **Timing-correlation prevention:** `Vote.batchOrder` is a random int, so DB insert order ≠ vote order.
- See `context/database/database-scheme-v2.md` for the full table-level reference.
